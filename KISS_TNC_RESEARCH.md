# KISS TNC and Kenwood internal TNC research

Research and historical bench notes, initially reviewed October 27, 2026. The owner subsequently reported successful TS-2000 and TM-D710A operation, including KISS receive and transmit on the D710A. See the README and roadmap for the current support status; dated observations below describe the state at the time of each test.

## Current OpenBeacon and Dire Wolf

- OpenBeacon manages a bundled Dire Wolf 1.8.2 development snapshot sidecar for Linux x86-64. It uses one 1200-baud AFSK channel, ALSA audio, and KISS over loopback TCP. Receive-only is the default; VOX, serial RTS/DTR and CM108 GPIO PTT are available for optional transmission, which requires more hardware testing. Windows can use an externally installed Dire Wolf through TCP KISS; the bundled modem is Linux x86-64 only.
- The generated configuration now specifies `FIX_BITS 1 APRS`: attempt single-bit recovery with APRS sanity checking, without `PASSALL`. In the pinned [1.8.1 source](https://github.com/wb2osz/direwolf/blob/1.8.1/src/audio.h), the default is **no** correction and its author cautions that even single-bit repair can occasionally pass corrupted packets. Higher repair levels can increase false positives and CPU use; do not silently enable them. This decision is the owner's requested behavior, not a guarantee that a recovered frame is correct.
- Normal KISS data frames do not identify whether Dire Wolf repaired a frame or how many bits were changed. OpenBeacon cannot currently distinguish those frames from unrepaired ones; do not label them clean or independently CRC-verified. Dire Wolf logs may contain details, but parsing them as authoritative packet metadata would need careful correlation. The `ax25Bytes` stored by OpenBeacon are bytes delivered by the TNC, possibly already repaired; they are not necessarily the originally received RF bits.
- The owner's 88-second 144.390 MHz capture produced seven unrepaired frames in the prior reference comparison and seven KISS frames in OpenBeacon's bundled-modem replay; all seven went through the shared APRS decoder. Groundside's deeper search found one additional three-bit-repaired frame; that is not evidence for enabling level 3 by default. See the local Groundside live handoff notes.
- **Security update:** OpenBeacon now bundles a 1.8.2 development snapshot with the relevant upstream fixes. [Dire Wolf's changelog](https://github.com/wb2osz/direwolf/blob/master/CHANGES.md) reports that 1.8.2 fixes CVE-2025-34457 and CVE-2025-34458. Continue hardware testing of the modified build; the loopback patch is not a substitute for that review.

## KISS protocol and transports

The [original KISS specification](https://www.ax25.net/kiss.aspx) describes a host-to-TNC byte stream, not an on-air protocol. Data frames start/end with `C0` (FEND), and `DB DC`/`DB DD` escape literal `C0`/`DB`. The first byte identifies the radio port and command; command 0 carries data. Framing can be fragmented or coalesced across serial/TCP reads. Handle empty delimiters, bad escapes, bounded frame size, disconnects and resynchronization. OpenBeacon's shared packet crate already includes a bounded KISS decoder and AX.25 UI parser.

- KISS is carried over serial/USB, TCP, and in some products Bluetooth. The transport does not imply a particular radio, baud rate, audio device, or whether the modem is software or hardware. Do not confuse **host serial baud** with **over-the-air modem speed**.
- Standard KISS carries no separate host-link checksum, and the original specification describes the TNC checking and removing the RF FCS before delivering a frame. Some devices or extensions behave differently: confirm the exact FCS convention for each supported adapter. Do not assume a received AX.25 byte array contains the original FCS or that the application can independently verify RF reception.
- KISS also has host-to-TNC transmit and configuration commands, including TX delay, persistence, slot time, tail, duplex, hardware-specific settings, and return-from-KISS. Their support, ranges, and semantics vary. Receive-only mode must not send data frames, configuration bytes, startup sequences, or a return command unless explicitly implemented and authorized. Closing a connection is not a command to change radio modes.
- Hardware TNC discovery needs serial port names and, where available, USB device descriptions and stable identifiers, permissions, selected baud/framing/flow control, and clear busy/disconnected/error states. Do not assume a USB adapter is a TNC or transmit a probe to identify it. Bluetooth classic serial and BLE require different implementations; a Bluetooth name alone is not a protocol guarantee.
- TCP KISS should have user-selected endpoint, explicit connect/disconnect, bounded buffering, source and channel attribution, reconnect/backoff, and an indication that transport connection does not prove RF reception. Protect receive and transmit separately; multiple adapters must not lose their provenance. OpenBeacon now has initial receive-only serial and TCP KISS adapters; the serial driver has a simulated pseudo-terminal test but needs real-device verification. The bundled modem is a separately managed source.
- APRS UI frames are one use of AX.25. Connected-mode BBS frames need a separate link/session implementation; a KISS byte stream and UI packet decoder alone do not provide a BBS inbox.

## Recommended implementation sequence

1. Update/review the bundled Dire Wolf version and test KISS receive, invalid frames, repair behavior, disconnect and shutdown with simulated sources. Preserve repair status as unknown until the transport supplies reliable metadata.
2. Build a receive-only serial KISS adapter with user-selected port, baud, data bits/parity/stop bits and flow control; do not issue startup commands. Retain KISS port, original received frame bytes, source, timestamps and errors in the shared pipeline.
3. Test fragmented/escaped frames, non-data commands, malformed/oversized frames, ports, disconnect/replug, device contention, FCS conventions, long-running reception and simultaneous APRS-IS. Verify which event and buffers are dropped under load.
4. Add documented model-specific guidance, especially the TS-2000 serial-ownership and power-cycle workflow. Confirm on actual hardware with the operator before claiming support; compare against an independent receiver or monitor.
5. Only later add explicit, separately enabled RF transmit, routing/path selection, previews, logging and digipeated-frame feedback. Test a simulator first, then controlled hardware with the operator. Reconnect and configuration changes must not enable transmit.

Additional sources: [Dire Wolf project](https://github.com/wb2osz/direwolf), [Mobilinkd KISS BLE protocol](https://github.com/mobilinkd/webconfig/blob/master/docs/PROTOCOL.md), and [Kenwood software and manuals](https://www.kenwood.com/i/products/info/amateur/software_download.html). These are references, not evidence of compatibility testing in OpenBeacon.

## YAAC source review

The owner supplied local YAAC source (`YAAC/src/main/java/org/ka2ddo/yaac/io/KenwoodConnector.java`, LGPL-3.0-or-later). Its Kenwood connector targets APRS-mode radios such as TM-D710, not the TS-2000's PC-control protocol. It receives CR- or LF-delimited text, removes leading `cmd:` prompts, separates `$` GPS/weather sentences from APRS, and interprets APRS-like `source>destination,path:payload` lines. It also sends setup queries; these are model-specific and must not be assumed appropriate for the TS-2000. OpenBeacon independently handles delimited text and prompt prefixes while preserving the original text; unrecognized lines are kept as monitor text, and it does not fabricate AX.25 or GPS data. No YAAC source was copied.

The TS-2000 manual's PC-command section documents `TC 0;` for packet communication mode and `TC 1;` for PC-control mode, plus Menu 55. Assigning the sub receiver to the TNC is separate from routing the PC serial port. YAAC's `TC 1` command in its different Kenwood connector must not be reused as a TS-2000 packet-mode command. Serial ownership and current command/converse mode must be established before sending any bytes; no automatic power cycle.

### TS-2000 native monitor bench result

With the owner assigning the sub receiver to the TNC, setting Menu 55 ON and attaching a dummy load, the FTDI port at 57,600 baud, 8N1, RTS/CTS returned `TC 0;cmd:HBAUD was 1200` and a `cmd:` prompt. Read-only queries showed `MONITOR OFF` and `MRPT ON`. An operator-authorized `MONITOR ON` command was sent after confirming the prompt; no RF transmission was requested or sent. In a 30-second capture the TNC produced three CR/LF-delimited TNC2-style monitor lines: two position packets from one station through different digipeater paths and one status packet. OpenBeacon's shared APRS core decoded all three; this is a bench validation of the radio's text format and parser, not yet an end-to-end desktop/TNC UI verification. Monitor was left enabled for the owner's requested use.

### Operator-authorized RF test

On October 27, 2026, the operator confirmed the antenna was connected and the TNC data band was on 144.390 MHz FM. With the TNC command prompt confirmed, OpenBeacon's development test temporarily set `MYCALL K8OTY` and `UNPROTO APRS VIA WIDE1-1`, submitted one manually configured position report with comment `OpenBeacon Test`, and returned to command mode. The operator reported that their D710 decoded the packet; no matching digipeated copy was observed during a 60-second TS-2000 monitor window. The operator subsequently confirmed on aprs.fi that JAMTWP heard the transmission at 13:23:07 EDT, at a reported distance of 22.7 miles. The operator reports that it was digipeated; OpenBeacon did not independently hear the relayed copy. The previous `MYCALL K8OTY-1` and `UNPROTO APIN21 VIA WIDE1-1,WIDE2-1` were restored and queried afterward. This bench action is not yet an implemented OpenBeacon transmit feature. The aprs.fi information was supplied by the operator; the raw relayed packet and its path were not independently inspected in this test.

### TS-2000 transmit identity follow-up

A later OpenBeacon position report captured on RF and APRS-IS at 15:27 EDT had the OpenBeacon comment but used the radio's prior `K8OTY-1` / `APIN21 VIA WIDE1-1,WIDE2-1` settings. Immediate restoration of MYCALL and UNPROTO after writing to converse mode is a plausible cause: the TNC can queue a packet before transmitting. The sender now keeps the selected values after a write rather than restoring them while a packet may still be queued. This change needs an independent on-air test, particularly when rapidly changing identity or path while earlier transmissions may be queued. The sent-packet display represents the requested packet, not independent confirmation of the actual RF header.
